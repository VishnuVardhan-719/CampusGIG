# Rankers board + `/explore` repair — build note (2026-10-07)

Scope: repair the broken `/explore` route, add a reviewed-builders Rankers board with scroll
entrance motion, and add a machine check that the published reputation numbers really come from
database state. No new dependencies, no Prisma schema change, no migration.

## 1. State of the app before this change

Verified by reading the tree and running the checks:

- Local checkout is a Prisma + NextAuth build: 20 routes (`/`, `/tasks`, `/tasks/[id]`, `/tasks/new`,
  `/dashboard`, `/contracts`, `/contracts/[id]`, `/students/[id]`, `/profile`, `/notifications`,
  `/admin`, `/login`, `/signup`, `/explore`, upload + AI route handlers), a service layer of 22
  server-authorized mutations in `src/server/services.ts`, 20-table schema, deterministic matcher in
  `src/lib/matching.ts`, seed of 10 students / 6 clients / 1 admin / 20 tasks / 6 contracts.
- **Blocker found:** `src/app/explore/page.tsx` did not compile. `npx tsc --noEmit --incremental false`
  reported 5 errors — `TaskStatus` imported from `@prisma/client` (the generated client is written to
  `src/generated/prisma`), `Link` used without importing `next/link`, and a knock-on `task.skills`
  inference failure from the rejected `where` clause. `npm run lint` also failed on
  `src/components/talent-field.tsx` (unused `R`, unused index parameter, `as any` on the SVG ref).
- `/explore` was not reachable from the navigation and was not covered by the UI smoke test.
- `/explore` loaded students one at a time (a query per student inside a sequential loop).
- Reviews exist for 4 of the 10 seeded students, and no ranking/leaderboard concept existed anywhere.
- Nothing verified that displayed reputation aggregates matched the rows they claim to summarise.

Repairs carried by the same change: `src/app/explore/page.tsx` (correct enum import, missing `Link`
import, batched student skill read, `Promise.all` matching) and `src/components/talent-field.tsx`

### Ranking rules enforced in code

- A builder is ranked only once a client review exists on a completed contract. Builders with no
  review history are listed separately with no published index — unknown history is never rendered as
  0 or 5.0.
- Components the platform has not observed are excluded from the total and the remaining weights are
  renormalised, so a missing signal can never count as a zero.
- The legend and the engine read one list (`BUILDER_COMPONENTS`), so displayed weights cannot drift
  from the maths.
- Ordering is fully deterministic (score, review count, completed contracts, name, id), so the same
  database state always renders the same order.

## 5. Limitations and follow-ups

- The board reflects the database, so a local database with stray `Integration fixture` students from
  an interrupted integration run shows them in the awaiting group. Clean up with
  `npm run demo:reset -- --confirm` before a demo.
- Only 4 seeded students carry reviews, so the board currently renders 4 ranked builders. Enriching
  the seed with more review history would make the board busier; it was deliberately left out of this
  change.
- Ranking loads every active student in one read. Fine at demo scale; a real deployment needs a
  page-bounded query plus an index on `Review.revieweeId`.
- Not built in this pass (offered, not selected): applicant shortlist/reject controls, milestone
  tracking UI, CI workflow with `.env` validation.
